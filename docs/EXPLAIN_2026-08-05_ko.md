## 1. SEP이 뭐고, 왜 그런 분모가 붙나

### 이름부터

**SEP = SEParation index**(분리 지수). **제가 이번에 만든 이름입니다.** 문헌에 있는 표준 지표가 아니고, 논문에 쓸 때도 "우리가 정의한 요약값"이라고 밝혀야 합니다. 그리고 **SEP은 결과가 아니라 요약**입니다. 진짜 결과는 block × factor 행렬이고, SEP은 그 행렬을 한 줄로 줄인 편의 숫자입니다. **행렬 없이 SEP만 보고하면 안 됩니다.**

### 무엇을 재려는 건가

우리가 주장하려는 건 이겁니다.

> 표현이 두 인자를 두 블록으로 **갈라놓았다.**

"갈라놓았다"가 참이려면 **세 가지가 동시에** 성립해야 합니다. 하나라도 깨지면 분리가 아닙니다.

| 조건 | 깨졌을 때 벌어지는 일 |
|---|---|
| z_slow가 느린 인자를 **갖고 있다** | z_slow가 텅 비면 배제야 완벽하지만 쓸모가 없음 |
| z_fast가 빠른 인자를 **갖고 있다** | 빠른 인자를 그냥 **파괴**한 것. 분리가 아님 |
| z_slow가 빠른 인자를 **안 갖고 있다** | 배제가 안 됨. 우리 주장의 핵심이 무너짐 |

SEP은 이 세 조건을 각각 [0,1] 점수로 만든 뒤 **곱한 것**입니다.

### 항 1 — 포함 (inclusion)

```
포함 = (z_slow의 느린 인자 점수) / (z_full의 느린 인자 점수)
```

**질문:** z_slow가 느린 인자를 지켰나?

**왜 z_full로 나누나?** "활동 macro-F1 0.85"라는 숫자만으로는 잘한 건지 못한 건지 알 수 없습니다. 데이터셋마다 난이도가 다르니까요. **z_full은 이 모델이 통째로 아는 전부**입니다. 그래서 이 비율은 이렇게 읽힙니다.

> 이 모델이 가진 느린 정보 중에서, **몇 퍼센트가 z_slow에 살아남았나.**

1.0이면 전부 살아남은 것입니다. 분모를 1.0으로 두면(즉 나누지 않으면) 어려운 데이터셋은 무조건 낮은 점수가 나와서 데이터셋 간 비교가 불가능해집니다.

### 항 2 — 배정 (allocation)

```
배정 = (z_fast의 빠른 인자 점수) / (비교군 전체의 천장)
```

**질문:** 빠른 인자가 z_fast에 **실제로 들어 있나?**

이게 **공허함을 잡는 항**입니다. 이 항이 없으면, 빠른 인자를 아무 데도 인코딩하지 않은 모델이 leak=0으로 만점을 받습니다.

**왜 자기 모델의 z_full이 아니라 "비교군 전체의 천장"으로 나누나?** ← 이게 제일 헷갈리는 부분이고, 사실 제가 이 지표를 설계하면서 한 번 틀렸다가 고친 곳입니다.

자기 z_full로 나눈다고 해봅시다. HAPT의 `nce+online`은:

```
z_fast = 0.163,  자기 z_full = 0.193   →  0.163 / 0.193 = 0.84  (거의 만점!)
```

**말이 안 됩니다.** 이 모델은 빠른 인자를 거의 아무 데도 안 담았는데, **자기 천장도 같이 무너져 있어서** 비율이 높게 나옵니다. 비율은 "천장 자체가 붕괴했다"를 감지하지 못합니다.

비교군 전체의 천장(HAPT에서는 0.955)으로 나누면:

```
0.163 / 0.955 = 0.17  (정확히 나쁨)
```

**대가:** 이 때문에 SEP은 **상대 지표**가 됩니다. 비교군에 뭐가 들어 있느냐에 따라 값이 변합니다. 이건 실제 한계이고 논문에 명시해야 합니다.

### 항 3 — 배제 (exclusion)

```
배제 = 1 − (z_slow의 빠른 인자 점수) / (rand16의 빠른 인자 점수)
```

**질문:** z_slow가 **같은 임베딩의 아무 16차원보다** 빠른 인자를 덜 갖고 있나?

**왜 무작위 부분공간으로 나누나?** 당신이 물으신 그 질문이 여기 답입니다. **"leak 0.045"는 그 자체로 아무 의미가 없습니다.** 비교 대상이 있어야 읽힙니다.

| 데이터셋 | z_slow의 leak | 무작위 16차원 | 배제 |
|---|---|---|---|
| 합성 | 0.045 | **0.856** | 1 − 0.045/0.856 = **0.947** |
| HAPT | 0.045 | **0.042** | 1 − 0.045/0.042 = **음수 → 0** |

**같은 0.045인데 의미가 정반대입니다.** 합성에서는 놀라운 배제이고, HAPT에서는 아무것도 안 한 것입니다. 분모가 없으면 이 둘을 구분할 방법이 없습니다. 우리가 지금까지 이 둘을 구분 못 하고 있었습니다.

- 배제 = 0 → 무작위 회전과 다를 바 없음 (메커니즘이 한 일이 없음)
- 배제 = 1 → 빠른 정보가 완전히 없음
- 음수(무작위보다 더 샘) → 0으로 자름

### 왜 더하지 않고 곱하나

**세 조건이 전부 필요조건이기 때문입니다.** 하나라도 0이면 분리 주장은 완전히 실패합니다. 더하면 두 항이 높을 때 나머지 하나의 0이 가려집니다. 곱하면 **논리곱(AND)**이 되어 "셋 다 성립해야 한다"가 그대로 표현됩니다. "분리"라는 말의 뜻이 정확히 그겁니다.

### 정말 효과적인가 — 증거 두 개

**(가) 자체 검증.** 인공적으로 완벽히 분리된 임베딩(z_slow에 라벨만, z_fast에 빠른 인자만)은 **SEP 1.000**. 똑같은 정보를 무작위 회전으로 섞은 것은 **SEP 0.000**. 정보량은 같고 좌표만 다른데 값이 정반대로 나옵니다 — 이게 지표가 "정렬"을 재고 있다는 뜻입니다.

**(나) 실제 ablation을 한 줄로 재현.** 합성 l1+ema:

| 셀 | 포함 | 배정 | 배제 | **SEP** |
|---|---|---|---|---|
| 메커니즘 없음 | 1.00 | 0.93 | 0.02 | **0.018** |
| 게이트만 | 1.00 | 0.96 | 0.47 | **0.448** |
| xcov만 | 0.72 | 0.98 | 0.61 | **0.431** |
| **둘 다** | 0.98 | 0.99 | 0.95 | **0.937** |

2×2 표 전체가 말하던 "게이트가 배정하고 xcov가 배제하며 둘 다 필요하다"가 **숫자 하나의 순서로** 재현됩니다. 그리고 실패 원인이 어느 항인지도 바로 보입니다 — xcov만 쓴 셀은 **포함이 0.72로 떨어져서** 진 것입니다.

### 정직한 한계

1. **이론이 아니라 요약입니다.** 행렬과 같이 보고해야 합니다.
2. **비교군 의존적입니다** (배정의 천장 때문).
3. **눈금이 없습니다.** SEP 0.9와 0.8의 차이가 "12% 낫다"는 뜻이 아닙니다. **순위용**입니다.
4. 선형 프로브 기반이라, 비선형으로 남아 있는 정보는 못 봅니다(기존 한계 그대로).

## 2. "그냥 하드웨어 질문이었는데 논문 한계까지 갈 일인가"

**아닙니다. 제가 과했습니다.** 사실 질문 하나에 논문 액션 아이템을 붙인 건 범위 확대였고, 없는 문제를 있는 것처럼 키운 것이기도 합니다.

**모델이 작은 건 결함이 아니라 적정 설계입니다.** 학습 데이터가 HAPT 2,104 윈도우 / PTB-XL 5,000 레코드입니다. 여기에 큰 모델을 쓰면 과적합합니다. 0.36M 파라미터는 이 규모에 맞는 선택이지 타협이 아닙니다.

논문에 들어갈 건 **실험 설정 절에 모델 크기 한 줄**뿐입니다. 그건 재현성 정보이지 한계가 아닙니다. 스케일링 한계는 이미 CLAUDE.md §6에 있고, **그건 "우리 모델이 작다"가 아니라 "두-시간척도 가정이 큰 모델·긴 시퀀스에서도 성립하는지 안 봤다"는 다른 얘기**입니다. 제가 둘을 섞었습니다.

답만 남기면: **학습이 빠른 건 모델이 작아서(0.36M)이고, 데이터도 작습니다.** H200 한 장은 오히려 남아돌아서 3개를 동시에 돌려도 69%입니다.

## 3. "위치 X의 윈도우 Y개"가 무슨 말인가

### 용어부터 하나씩

**원본 신호.** 합성 데이터는 길이 100만의 1차원 숫자열입니다. `x[0], x[1], …, x[999999]`.

**패치(patch).** 모델은 샘플을 하나씩 보지 않고 **8개씩 묶어서** 봅니다. 이 묶음이 패치입니다. 합성은 P=8.

**윈도우(window).** 학습·평가의 기본 단위입니다. 원본에서 **연속된 2048개 샘플**을 잘라낸 것이고, 이걸 8개씩 묶으면 **패치 256개**가 됩니다. 즉 윈도우 하나 = (256 패치 × 8 샘플).

```
원본:  x[0] x[1] x[2] ............................ x[999999]
                 └─────── 윈도우 하나 (2048 샘플) ───────┘
                 └─패치0─┘└─패치1─┘ …  └─패치255─┘
```

**윈도우를 400개 뽑습니다.** 시작 지점을 **무작위로** 400번 골라서 자릅니다. 여기가 나중에 문제가 되는 지점입니다.

**위치(position).** 인코더는 causal(인과적)이라, 윈도우를 넣으면 **패치마다 벡터를 하나씩** 내놓습니다. 위치 p의 벡터는 **패치 0부터 p까지만 보고** 만든 64차원 요약입니다.

```
입력:  패치0 패치1 패치2 ... 패치255
출력:   z_0   z_1   z_2  ...  z_255      ← 위치마다 64차원 벡터 하나
        (z_p 는 패치 0..p 만 봄)
```

**프로브 위치.** 256개 전부를 채점하지는 않고 **64, 76, 88, …, 232 — 15개 위치**만 씁니다(문맥 하한 C_MIN=64 때문에 64부터).

### 그래서 "위치 X의 윈도우 Y개"란

윈도우 하나가 **15개 행**을 만듭니다(위치 15개니까). 윈도우 400개면 **400 × 15 = 6,000행**짜리 특징 행렬이 됩니다.

문제는 **행을 쌓은 순서**였습니다. 위치를 바깥 루프로 돌렸습니다.

```
행    0 ~  399 :  위치 64  에서 뽑은 윈도우 0,1,2,…,399  의 벡터
행  400 ~  799 :  위치 76  에서 뽑은 윈도우 0,1,2,…,399  의 벡터
행  800 ~ 1199 :  위치 88  에서 뽑은 윈도우 0,1,2,…,399  의 벡터
      ⋮
행 5600 ~ 5999 :  위치 232 에서 뽑은 윈도우 0,1,2,…,399  의 벡터
```

**같은 400개 윈도우가 15번 반복해서 등장**합니다. 매번 다른 위치에서 읽은 것뿐입니다.

### 버그가 왜 생겼나

여기서 `행 3000`에서 잘라 앞을 학습, 뒤를 테스트로 썼습니다. 3000행은 **위치 148 블록의 한가운데**입니다. 그러니까:

- 학습 세트 = 위치 64~136에서 읽은 **윈도우 0~399 전부**
- 테스트 세트 = 위치 148~232에서 읽은 **윈도우 0~399 전부**

**윈도우 400개가 통째로 양쪽에 다 들어갑니다.** 나눈 건 윈도우가 아니라 **위치**였습니다.

여기에 두 번째 문제가 겹칩니다. 윈도우 시작점이 무작위라 **윈도우끼리도 서로 겹칩니다.** 100만 길이에서 2048짜리를 400번 무작위로 뽑으면 이웃한 것들이 최대 2047/2048까지 겹칩니다(실측 중앙값 95%).

결국 테스트 세트가 학습 세트와 **사실상 같은 데이터**였습니다.

### 어떻게 고쳤나

행 번호가 아니라 **그 행이 속한 윈도우가 원본의 어느 시각에서 왔는지**로 나눕니다.

```python
wid = np.tile(np.arange(400), 15)        # 행 → 그 행이 속한 윈도우 번호
cut = np.sort(starts)[200]               # 윈도우 시작 시각의 중앙값
tr  = np.flatnonzero(starts[wid] + 2048 <= cut)   # 윈도우가 cut '이전에 끝남'
te  = np.flatnonzero(starts[wid] >  cut)          # 윈도우가 cut '이후에 시작함'
```

- 학습 조건의 **`+ 2048`이 핵심**입니다. 학습 윈도우의 **마지막** 샘플이 cut보다 앞이고, 테스트 윈도우의 **첫** 샘플이 cut보다 뒤입니다. 그래서 **공유하는 원본 샘플이 하나도 없습니다.** `starts <= cut`으로만 했다면 cut 직전에 시작한 윈도우가 cut 너머까지 뻗어서 겹칩니다.
- cut을 가로지르는 윈도우들은 양쪽 어디에도 안 들어가고 **버려집니다.** 그게 완충 구간입니다.
- `assert`로 같은 윈도우 번호가 양쪽에 없음을 확인합니다.

### 이 원칙이 합성에만 적용된 건가

**네, 이 버그는 합성 전용이었습니다.** 실데이터는 처음부터 다른 방식으로 나눕니다.

| 데이터 | 분할 기준 | 코드 |
|---|---|---|
| 합성 | **윈도우 시작 시각** (위 방식) | `stems_synth.probe`, `twosided.synth_feats` |
| HAPT | **피험자** (사람 단위로 통째 홀드아웃) | `train_real.py:58` |
| PTB-XL | **환자** | 같음 |

실데이터는 프로토콜 C3의 **그룹 분할**을 씁니다 — 피험자의 약 1/3을 통째로 빼두는 방식이라, 같은 사람의 데이터가 양쪽에 걸치는 일이 애초에 없습니다. 그래서 위치-우선 정렬 버그의 영향을 받지 않았습니다.

다만 **HAPT의 도메인 이동 실험은 A 그룹 안을 또 나눠야** 해서 별도 문제가 있었고(시간 순서로 나누면 활동 구성이 어긋남), 그건 오늘 **블록 분할**로 고쳤습니다.

## 4. 합성 데이터는 어떻게 만들어지나 — 바닥부터

목표는 이겁니다.

> **정답을 우리가 아는** 신호를 만든다. 안에 **느린 인자**와 **빠른 인자**가 하나씩 들어 있고, 둘을 우리가 정확히 알고 있어야 한다.

실데이터는 "무엇이 진짜 느린 인자인지" 아무도 모릅니다. 합성은 우리가 직접 넣었으니 압니다. **합성의 역할은 성능 자랑이 아니라, 정답을 아는 상태에서 메커니즘을 재는 것**입니다.

### 재료 1 — 느린 인자 `s(t)`: 3상태 마르코프 체인

"regime"(레짐)이라고 부릅니다. 상태가 **0, 1, 2 셋 중 하나**이고, 시간에 따라 가끔 바뀝니다.

```python
for t in range(n):
    if 확률 1/3000 로 참:
        cur = 다른 상태로 점프
    s[t] = cur
```

매 스텝 **1/3000 확률로** 상태를 바꿉니다. 그러니 평균적으로 **한 상태에 약 3000스텝 머뭅니다.** 이 머무는 시간을 **dwell**이라고 합니다.

윈도우가 2048스텝이니까, **윈도우 하나 안에서 regime이 안 바뀔 때도 있고 한 번 바뀔 때도 있습니다**(약 절반). 이건 의도한 것입니다 — 진짜로 "느리지만 상수는 아닌" 인자를 만들려는 거니까요.

### 재료 2 — 빠른 인자 `u(t)`: OU 과정

**OU = Ornstein–Uhlenbeck process**(오른슈타인–울렌벡 과정). 이름은 어렵지만 뜻은 간단합니다.

> **말뚝에 고무줄로 묶인 취객.** 비틀거리며 아무 데나 가지만, 멀어지면 고무줄이 잡아당겨 0 근처로 되돌립니다.

수식은 한 줄입니다.

```python
a = exp(-1/50)            # ≈ 0.980
u[t] = a * u[t-1] + 잡음[t]
```

- `a * u[t-1]` — **어제 값의 98%를 기억**합니다 (고무줄이 당기는 힘).
- `+ 잡음` — 매 스텝 새로운 무작위 충격 (비틀거림).

50이라는 숫자가 **기억의 수명**입니다. 50스텝이 지나면 과거의 영향이 1/e(약 37%)로 줄어듭니다. 그래서 `U_TAU = 50`.

**이게 왜 "빠른" 인자인가?** 느린 인자는 3000스텝 머무는데 이건 50스텝이면 잊습니다. **60배 차이** — 이 격차가 우리 방법이 성립하기 위한 전제(timescale gap)이고, 합성에서는 우리가 직접 만들어 넣은 것입니다.

### 두 인자가 하나의 신호로 합쳐지는 방식 ← 여기가 핵심

기본 신호는 **사인파**입니다. 그런데 그냥 사인파가 아니라, **두 인자가 각각 다른 방식으로 개입**합니다.

**단계 1 — 느린 인자가 "기본 주파수"를 정합니다.**

```python
REGIME_FREQ = [0.095, 0.100, 0.105]
기본주파수(t) = REGIME_FREQ[s(t)]
```

주파수 0.1 cycles/sample이란 **10샘플마다 한 바퀴** 돈다는 뜻입니다. 세 regime은 각각 10.53 / 10.00 / 9.52 샘플 주기입니다. **±5% 차이**, 이게 앞서 말한 `gap`입니다.

**단계 2 — 빠른 인자가 그 주파수를 흔듭니다.**

```python
순간주파수(t) = 기본주파수(t) * (1 + 0.05 * u(t))
```

`FREQ_MOD = 0.05`라서 u가 주파수를 **±5%씩 흔듭니다.** u는 평균 0, 표준편차 1짜리라 대략 ±1 범위를 오갑니다.

**여기서 중요한 걸 눈치채셔야 합니다.** regime이 주파수를 바꾸는 폭(±5%)과 u가 주파수를 흔드는 폭(±5%)이 **똑같습니다.** 즉 **빠른 인자의 흔들림이 느린 인자의 신호와 같은 크기**입니다. 그래서 과제가 자명하지 않은 것이고, gap을 ±1%로 좁히면 느린 신호가 빠른 흔들림의 1/5로 **묻혀버립니다**.

**단계 3 — 위상을 누적합니다.**

주파수가 매 순간 변하니까 `sin(2πft)`처럼 쓸 수 없습니다. **한 스텝씩 위상을 쌓아야** 합니다.

```python
phi = cumsum(2π * 순간주파수)      # 누적합
```

비유하자면, 자동차 속도계가 계속 변할 때 이동거리를 구하려면 매 순간 속도를 더해 나가야 하는 것과 같습니다. 위상 = 지금까지 회전한 총 각도.

**단계 4 — 최종 신호.**

```python
x(t) = sin(phi(t))  +  0.2 * u(t)  +  0.1 * 백색잡음(t)
        └─ 주파수에 ─┘  └ 빠른 인자가 ┘  └─ 측정 잡음 ─┘
         두 인자 모두     크기로도 직접
           들어 있음        더해짐
```

**빠른 인자 u는 두 번 들어갑니다.** 한 번은 주파수를 흔드는 방식으로(단계 2), 또 한 번은 **그냥 더해지는 방식으로**(0.2·u). 두 번째 항 덕분에 u가 신호에 직접 흔적을 남깁니다.

**느린 인자 s는 주파수를 통해서만** 들어갑니다. 진폭은 세 regime 모두 1.0으로 **같습니다**(`REGIME_AMP = [1,1,1]`). 이건 의도적입니다 — regime이 진폭을 바꾸면 **에너지만 재도 regime을 알 수 있어서** 과제가 시시해집니다. 프로토콜의 스크린에 "regime 간 분산비 < 1.2" assert가 있는 이유가 이것입니다.

### 정리하면

```
느린 인자 s(t)  ──→  기본 주파수 (0.095 / 0.100 / 0.105)
                              │
빠른 인자 u(t)  ──→  ×(1 ± 5%) 로 흔듦
                              │
                              ▼
                     순간 주파수 → 누적 → 위상 φ(t)
                                              │
                                              ▼
                              x(t) = sin(φ) + 0.2·u + 0.1·잡음
                                                └── u가 여기 또 들어감
```

2. 8개씩 묶어 **(256 패치 × 8)** 모양으로 바꿉니다.
3. 인코더에 넣으면 위치마다 64차원 벡터가 나옵니다.

**채점할 때 쓰는 정답은:**

- 빠른 정답 = 같은 지점의 `u(t)` (실수 → 회귀, R²로 평가)
